# Agent 应用开发学习等级

本文把 Agent 应用开发拆成 5 个学习等级：从完全新手，到能独立完成一个可演示、可评估、可讲解的 Agent 项目。

核心路线：

```text
L1 API 使用者
  -> L2 结构化调用者
  -> L3 核心能力构建者
  -> L4 工程化实践者
  -> L5 独立项目负责人
```

学习时不要平均用力。每一层都先抓最重要的 30%，也就是最影响后续理解和项目落地的部分。

---

## L1：API 使用者

适合阶段：完全新手 -> 能和模型稳定对话。

### 应该掌握什么

- LLM 的基本工作方式：模型是在基于上下文预测下一个 token，不是数据库，也不是搜索引擎。
- Chat API 的调用方式：`messages` 结构、常用参数、错误处理、计费方式。
- Prompt 基本功：System Prompt、Few-shot、CoT、结构化输出。

### 最重要的 30%

#### 1. Messages 对话结构

所有 Agent 框架底层本质上都在组织 `messages`。

- `system`：定义角色、规则、边界。
- `user`：用户输入。
- `assistant`：模型回复。

模型本身是无状态的。所谓多轮对话，就是每次请求时把必要的历史消息重新发给模型。理解这一点，后面的记忆、摘要压缩、上下文管理才会变得清楚。

#### 2. Token 与 Context Window

Token 是计费和容量的基本单位。Context Window 是模型一次能处理的最大上下文长度。

后面很多工程问题都来自这里：

- RAG 为什么要分块？
- 长对话为什么要摘要压缩？
- 为什么不能把所有资料都塞进 Prompt？
- 为什么 Agent 跑多步后成本会快速上升？

本质都是因为 context 是稀缺资源。

#### 3. System Prompt + 结构化输出

从聊天 Demo 走向程序可用，关键是让模型输出可以被代码消费的数据。

一个可用的 Prompt 通常包括：

- 角色：你是谁。
- 任务：你要做什么。
- 约束：不能做什么，遇到不确定如何处理。
- 输出格式：最好是 JSON Schema 或明确 JSON 示例。

如果模型输出不能稳定解析，后面的工具调用、工作流、评估都会很难做。

### 常见错误

- 把模型当搜索引擎或数据库，忽视幻觉问题。
- Prompt 写得很长但目标模糊，没有明确输出格式。
- 不关注 token 用量，直到成本和延迟失控才开始处理。
- Temperature 乱设：抽取、代码、结构化任务用了过高温度，导致输出不稳定。

### 晋级标准

- 能写一个 CLI 多轮对话脚本。
- 能让同一个抽取任务连续 5 次返回合法 JSON。
- 能解释 token、context window、temperature、messages 分别是什么。

## L2：结构化调用者

适合阶段：会和模型对话 -> 能让模型选择工具并产生结构化结果。

### 应该掌握什么

- Function Calling / Tool Use 的完整消息流。
- 一个 Agent 框架的核心抽象，例如 LangChain 的 `Prompt -> Model -> Parser`。
- 短期记忆：如何管理和注入对话历史。

### 最重要的 30%

#### 1. Tool Calling 消息流

这是 Agent 的原子操作。

```text
user 提问
  -> assistant 返回 tool_calls
  -> 你的代码执行对应函数
  -> 把函数结果作为 tool message 发回模型
  -> assistant 基于工具结果生成最终回复
```

关键认知：模型不会真的执行函数。模型只是输出“我想调用哪个工具、参数是什么”。真正执行工具、校验参数、处理异常、回传结果，全部由你的代码负责。

理解这个循环，才能理解后面的 ReAct Agent。

#### 2. 工具 Schema 定义

工具的 Schema 不只是类型声明，也是给模型看的说明书。

需要写清楚：

- 工具能做什么。
- 什么时候应该用。
- 参数分别代表什么。
- 参数有什么限制。

工具描述写得含糊，模型就容易选错工具、传错参数、重复调用。

#### 3. 框架的管道思维

不管用 LangChain、LangGraph，还是原生 SDK，底层都离不开：

```text
Prompt 模板 -> 模型调用 -> 输出解析 -> 业务代码消费
```

框架只是把手写 messages、解析输出、管理历史封装起来。学习框架时重点不是背 API，而是看清数据如何流动。

### 常见错误

- 以为模型会自动执行函数，结果没有写工具执行和回传逻辑。
- 工具描述太泛，例如“查询信息”，导致模型不知道何时使用。
- 不校验模型生成的工具参数，直接执行外部操作。
- 过早陷入框架细节，会写 `chain.invoke()`，但说不清底层发生了什么。

### 晋级标准

- 能手绘 tool calling 的完整时序图。
- 能实现一次请求中并行调用多个工具。
- 能处理单个工具失败、重试、降级，不让整轮对话直接崩掉。
- 能搭出带短期记忆的链，并解释每一步数据流。

## L3：核心能力构建者

适合阶段：能调用工具 -> 能构建 RAG、Agent、Workflow。

这是从“会调 API”到“会做 AI 应用”的关键分界。

### 应该掌握什么

- RAG：加载、分块、Embedding、向量检索、生成回答。
- Agent：ReAct 循环，多步工具调用，自主决策。
- Workflow：状态图、条件分支、Human-in-the-Loop、可恢复流程。
- 选型判断：什么时候用 Prompt、RAG、Function Calling、Agent、Workflow。

### 最重要的 30%

#### 1. RAG 的本质与分块权衡

RAG 的核心是：回答前先从私有知识库检索相关内容，再把检索结果放进 Prompt，让模型基于资料回答。

完整链路：

```text
文档
  -> Chunking
  -> Embedding
  -> Vector Store
  -> Retrieval
  -> Prompt
  -> LLM Answer
```

RAG 效果最常见的瓶颈不是模型，而是检索。

分块是最重要的调参点：

- 块太大：噪音多，检索粒度粗。
- 块太小：上下文丢失，答案被切碎。
- overlap 太少：跨段信息断裂。
- overlap 太多：重复内容增加成本。

没有万能参数，必须用测试集评估。

#### 2. ReAct 循环

ReAct = Reasoning + Acting。

```text
思考
  -> 行动，调用工具
  -> 观察工具结果
  -> 再思考
  -> 继续行动或输出最终答案
```

Agent 与普通程序最大的区别是：控制流在运行时由模型决定，而不是由代码完全写死。

这带来自由，也带来风险。所以 Agent 必须配护栏：

- 最大迭代次数。
- 工具白名单。
- 参数校验。
- 危险操作拦截。
- 失败降级。

#### 3. Agent vs Workflow 的选型

这是本层最重要的判断力。

| 场景特征 | 更适合 Workflow | 更适合 Agent |
| --- | --- | --- |
| 步骤是否固定 | 固定、可预测 | 运行时才知道 |
| 可靠性要求 | 高 | 中等，需要 Eval 兜底 |
| 调试难度 | 较低 | 较高 |
| 典型场景 | 审批流、内容生成流水线、订单处理 | 多工具问题排查、开放式研究、复杂问答 |

原则：能用固定流程解决，就不要轻易交给 Agent 自主决策。自由是成本和不确定性的来源。

### 常见错误

- RAG 效果差就先换模型，其实问题常在分块、top-k、Embedding、检索策略。
- 不看检索出来的 chunks，只看最终回答。
- 没有测试集，靠感觉调 RAG 参数。
- Agent 不设最大步数，导致死循环和成本失控。
- 所有需求都做成 Agent，忽视 Workflow 更稳定、更可测。

### 晋级标准

- RAG 在 10 条以上测试集上命中率达到 70% 以上。
- 能解释某次 RAG 优化是如何提升检索质量的。
- ReAct Agent 能完成一个至少 3 步工具调用任务。
- 能面对一个新需求，判断应该用 Prompt、RAG、Function Calling、Agent 还是 Workflow，并说明理由。

## L4：工程化实践者

适合阶段：能做 Demo -> 能做接近生产可用的 Agent 应用。

### 应该掌握什么

- SSE / Streaming：前端流式显示模型输出。
- 长期记忆：跨会话保存用户偏好和历史摘要。
- Eval：固定测试集、自动跑分、回归评估。
- 成本与可观测：token 记录、调用轨迹、缓存、模型路由。

### 最重要的 30%

#### 1. Eval 是第一优先级

LLM 应用输出具有概率性。没有 Eval，就无法判断一次修改到底让系统变好了还是变坏了。

最小可行 Eval：

- 准备 20 条典型 case。
- 每条包含输入、期望行为、评分标准。
- 写脚本自动运行。
- 输出 pass rate。
- 每次改 Prompt、模型、检索策略后都重跑。

Eval 是专业 Agent 开发和“感觉调参”的分界线。

#### 2. 流式输出

模型完整生成一个回答可能需要几秒到几十秒。流式输出可以显著降低用户感知延迟。

常见方式：

- 服务端：`text/event-stream`。
- 前端：`EventSource`、`ReadableStream`、`AbortController`。

流式不是只为了好看，而是直接影响用户是否愿意等待。

#### 3. 上下文与成本管理

核心原则：context 是稀缺资源，只放当前任务真正需要的信息。

常用手段：

- 摘要压缩：把旧对话压缩成 summary。
- 长期记忆：把用户偏好和重要事实外置保存，按需检索回来。
- 缓存：相同或相似问题复用结果。
- 模型路由：简单任务用便宜模型，复杂任务用强模型。
- token 记录：每次调用都能追踪成本。

### 常见错误

- 功能都做完才想起 Eval，已经不知道哪次改动导致退化。
- 无脑把所有历史消息塞进 Prompt。
- 只测 happy path，不测超时、非法 JSON、工具失败。
- 日志里没有工具调用轨迹，线上问题无法定位。
- 没有成本记录，直到 API 账单异常才开始排查。

### 晋级标准

- 应用支持前端流式输出。
- 每次 LLM 调用都记录 token 和估算成本。
- 有 20 条以上 eval case，并能输出 pass rate。
- 能根据调用轨迹定位一次失败发生在哪个环节。

## L5：独立项目负责人

适合阶段：能做工程化 Demo -> 能从 0 到 1 独立交付项目。

### 应该掌握什么

- 需求拆解：把模糊需求拆成 Prompt、RAG、Tool、Agent、Workflow 的组合。
- 架构设计：模块边界、数据流、失败路径、评估方式。
- 多 Agent 协作：Supervisor、专业 Agent、任务分发。
- 完整交付：可运行 Demo、架构文档、Eval 报告、复盘。

### 最重要的 30%

#### 1. 架构选型与拆解

好的 Agent 应用通常不是一个“万能大 Agent”，而是多种模式的组合。

以智能客服为例：

```text
用户问题
  -> 意图分类 Workflow
  -> 常见问题走 RAG
  -> 查订单走 Tool Calling
  -> 投诉/退款走 HITL
  -> 复杂问题转人工
```

独立做项目的关键不是会多少框架，而是能把需求拆成稳定、可测、可维护的模块。

#### 2. 可靠性设计

生产级 Agent 应用必须回答这些问题：

- 模型返回非法 JSON 怎么办？
- 工具调用失败怎么办？
- 用户问了不该回答的问题怎么办？
- RAG 检索不到资料怎么办？
- 多轮 Agent 死循环怎么办？
- 怎么证明新版比旧版更好？

如果设计里没有失败路径，这个方案还不完整。

#### 3. 范围控制

从 0 到 1 做项目，最容易失败的原因是范围失控。

正确顺序：

```text
先跑通一条最窄端到端链路
  -> 加一种能力
  -> 加对应 eval case
  -> 再扩展下一种能力
```

每一个新增功能都应该能被测试集覆盖。

### 常见错误

- 一开始就设计复杂多 Agent 系统，迟迟没有可运行链路。
- Demo 演示很好看，但换个问法就崩。
- 只交付代码，没有架构说明和 Eval 报告。
- 技术选型追新，而不是围绕需求选择最简单够用的方案。
- 没有失败降级，所有异常都直接暴露给用户。

### 晋级标准

- 独立完成一个完整 Agent 项目。
- 项目包含 RAG、工具调用、流程编排中的至少两类能力。
- 有可运行前端或 CLI Demo。
- 有 20 条以上 eval case 和评估报告。
- 能讲清架构设计、核心取舍、失败路径、后续优化方向。

## 当前建议路线

结合当前仓库进度，前面基础已经比较扎实：

- L1：API、Prompt、结构化输出，已完成。
- L2：LangChain、LangGraph 基础、Function Calling、MCP，已完成主要内容。
- L3：RAG 已完成，接下来重点是 ReAct Agent 与 Workflow。

下一步建议集中做两件事：

1. 在 `examples/agent-practice/` 中实现 ReAct Agent，重点观察模型如何决定下一步工具调用。
2. 在 `examples/workflow-practice/` 中实现固定 Workflow + HITL，重点对比它和 Agent 的选型差异。

完成这两项后，再进入 L4：流式输出、长期记忆、成本记录和 Eval 工程化。

---

## 选型速查

| 需求 | 优先方案 |
| --- | --- |
| 只需要稳定格式输出 | Prompt + JSON Schema |
| 需要查私有文档 | RAG |
| 需要调用外部 API | Function Calling / Tool Calling |
| 需要接入标准化外部工具生态 | MCP |
| 步骤固定、可预测 | Workflow |
| 步骤不确定、运行时决策 | Agent |
| 需要人工审批 | Workflow + HITL |
| 需要跨会话偏好 | 长期记忆 |
| 需要证明效果变好 | Eval |
